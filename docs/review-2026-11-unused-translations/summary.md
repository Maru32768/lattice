# 使われていない訳の削除のレビューのまとめ

`findings.tsv`の指摘を、ハーネス(人がレビューしなくても見つかる仕組み)を作る材料として整理する。2つのレビュー(`code-review`と`ponytail-review`)が同じ問題を見つけたときは1行にまとめ、`reviewer`を`both`にした。下の数は`findings.tsv`から数えた。ただし表の最後の列は、各行の指摘を前の回の修正のコミットと読み比べて数えたもので、`findings.tsv`の列からは出せない。

`caught_by`の内訳は、見つけようがないものが24、単体テストが5、エージェントへの指示が4、lint・e2e・ベンチマークが2ずつ。

## 繰り返し現れた型

**1. 「誰の訳か」を記録する時点の取り違え(7件、行1・12・13・20・21・22・31)。** 最初は、Page表示が訳を作った時点の持ち主だけを記録した。保存する前に訳した分は持ち主がないまま残り、ボタンで消えた。表示したときに持ち主を付けるようにすると、訳し終えたページはもう訳を求めないので、保存した直後には付かなかった。タブに求めた訳を覚えさせると、`pushState`で移ったページの分まで渡し、保存を待つ間に戻ったページの分も渡した。持ち主の引き直しも、待っている間の保存と`pushState`を1つずつ見落とした。ページをURLで見分けると、今度はページ自身が追跡用のパラメータを消したとき(`replaceState`)に別のページとみなした。ライブラリが記事のURLに使う正規化(`url_norm::normalize`)を最初から使えばよかった。どれも「この値は、どのページの、いつの時点のものか」を確かめていなかった。最初に利用者の流れ(保存していないページを訳す、保存する、開き直す、消す)をテストにしていれば、行1と行12は書く前に見つかった。

**2. 一度だけの重い処理の置き場所(5件、行8・14・18・23・27)。** 保存済みPDFに古い訳を渡す処理を、最初はmigrationの中に置いた。実際のライブラリの写しで測ると、デバッグビルドで5つのPDFに181秒かかり(6.6MBの論文1つで154秒)、その間アプリが起動しない。初めて数えるときに移すと、二重に走らないようにする仕組みと、対象を今もPDFの記事に絞る条件が必要になった。panicを捕まえる処理も、最初はmigrationの呼び出しだけに入れた。測ったのは指摘を受けてからで、migrationに新しい処理を足すときに実際のライブラリで時間を測っていれば、最初から外に置けた。

**3. 画面に出した数と、実際に消す数のずれ(3件、行6・19・30)。** 確認画面は設定を開いたときの数を出し、削除はボタンを押した時点の対象を消した。1回目は見送り、2回目でも指摘されたので直した。直したあとのe2eは、直す前でも通っていた。修正を一度戻してテストが落ちるのを確かめてから、コミットするようにした。

## 見送ったもの

- 持ち主は1つだけなので、2つの保存済みページが同じ文(サイトのフッターなど)を表示していると、持ち主の記事を消したときにもう一方の訳も消える(行2)。持ち主を1つの列で持つのは利用者が選んだ設計で、コードには`shortcut:`で書いた。
- 0.3.0までに保存したWebページのPage表示で作った訳のうち、本文の段落にないものは、そのページをまた開くまで削除の対象になる(行15)。ガイドに書いた。
- アプリ内ブラウザの「ライブラリに保存」以外の方法(追加の画面、インポート、スマホ、CLI)で開いているページを保存すると、保存する前に訳した分はそのページをまた開くまで削除の対象になる(行37)。
- ほかの見送り(行7・9・16・17・24・25・28・34・38)は、起こる幅がごく狭いか、起きても訳をもう一度作るだけで済むもの。
